# Requisitos No Funcionales (RNF)

# RNF-001 — Seguridad

**Tipo**: Requisito No Funcional de Seguridad

## Descripción

El sistema debe cumplir con los controles de seguridad definidos en el OWASP Top 10 y proteger la información de usuarios, pagos y pedidos.

## Requisitos Específicos

**RNF-001.1** — Las contraseñas deben hashearse con bcrypt (factor de costo mínimo 12) antes de persistirse.

**RNF-001.2** — Los tokens JWT deben firmarse con secretos de mínimo 32 caracteres aleatorios y expirar en máximo 24 horas.

**RNF-001.3** — Los endpoints de autenticación deben tener rate limiting (máx. 10 req/15 min por IP).

**RNF-001.4** — El CORS debe configurar orígenes explícitos — nunca `origin: "*"` en producción.

**RNF-001.5** — Toda consulta a la base de datos debe usar Prisma ORM (no SQL crudo con interpolación de strings).

**RNF-001.6** — Los datos de tarjetas de pago nunca deben almacenarse en la base de datos propia — solo el `id_transaccion` de la pasarela.

---

# RNF-002 — Rendimiento

**Tipo**: Requisito No Funcional de Rendimiento

## Requisitos Específicos

**RNF-002.1** — El catálogo de productos debe responder en menos de 500ms en el 95% de las solicitudes.

**RNF-002.2** — El endpoint de login debe responder en menos de 500ms incluyendo la verificación bcrypt.

**RNF-002.3** — El pool de conexiones a PostgreSQL debe configurarse con mínimo 2 y máximo 10 conexiones.

**RNF-002.4** — El frontend debe cargar el bundle inicial en menos de 3 segundos en una conexión de 10 Mbps.

---

# RNF-003 — Fiabilidad y Disponibilidad

**Tipo**: Requisito No Funcional de Fiabilidad y Disponibilidad

## Requisitos Específicos

**RNF-003.1** — El sistema debe mantener una disponibilidad mínima mensual del 99.5%.

**RNF-003.2** — Ante fallos imprevistos del servidor, el servicio debe recuperarse automáticamente en menos de 5 minutos.

**RNF-003.3** — Las transacciones críticas (checkout, pagos, movimientos de inventario) deben ejecutarse de forma atómica (ACID).

---

# RNF-004 — Mantenibilidad

**Tipo**: Requisito No Funcional de Mantenibilidad

## Requisitos Específicos

**RNF-004.1** — La cobertura de tests debe ser mínimo 70% en los módulos de lógica de negocio.

**RNF-004.2** — El código debe pasar ESLint y Prettier sin errores antes de cada commit.

**RNF-004.3** — Todos los tipos TypeScript deben ser explícitos — no usar `any` sin justificación documentada.

**RNF-004.4** — Cada archivo de módulo debe tener una cabecera de documentación (¿Qué? ¿Para qué? ¿Impacto?).

---

# RNF-005 — Usabilidad y Accesibilidad

**Tipo**: Requisito No Funcional de Usabilidad

## Requisitos Específicos

**RNF-005.1** — El contraste de color debe cumplir WCAG 2.1 AA (mínimo 4.5:1 para texto normal).

**RNF-005.2** — Todos los formularios deben ser operables completamente con teclado.

**RNF-005.3** — Los mensajes de error deben anunciarse con `role="alert"` para lectores de pantalla.

**RNF-005.4** — El diseño debe ser responsive — funcionar correctamente en viewport de 320px a 1920px.

---

# RNF-006 — Escalabilidad

**Tipo**: Requisito No Funcional de Escalabilidad

## Requisitos Específicos

**RNF-006.1** — El backend debe soportar al menos 200 usuarios concurrentes sin degradación perceptible.

**RNF-006.2** — El sistema debe permitir escalamiento horizontal del servicio Express mediante balanceo de carga.

**RNF-006.3** — Las consultas de catálogo deben soportar paginación para evitar cargar el listado completo de productos.

---

# RNF-007 — Portabilidad y Compatibilidad

**Tipo**: Requisito No Funcional de Portabilidad

## Requisitos Específicos

**RNF-007.1** — El backend debe ejecutarse correctamente en Windows y Linux mediante Node.js.

**RNF-007.2** — El sistema debe funcionar en los principales navegadores: Chrome, Firefox, Edge y Safari.

**RNF-007.3** — El entorno de desarrollo debe poder levantarse mediante variables de entorno (`.env`) sin configuración manual adicional.

---

# RNF-008 — Interoperabilidad

**Tipo**: Requisito No Funcional de Interoperabilidad

## Requisitos Específicos

**RNF-008.1** — La API debe exponer respuestas en formato JSON estandarizado para consumo del frontend y de integraciones futuras.

**RNF-008.2** — La integración con la pasarela de pagos debe realizarse mediante su SDK o API REST oficial.

**RNF-008.3** — Los webhooks entrantes deben validar la firma del proveedor antes de procesar el evento.

---

# RNF-009 — Auditoría y Trazabilidad

**Tipo**: Requisito No Funcional de Auditoría

## Requisitos Específicos

**RNF-009.1** — Todo movimiento de inventario debe registrar usuario, fecha y motivo en `movimientos_inventario`.

**RNF-009.2** — Todo cambio de rol de usuario debe quedar registrado para fines de auditoría.

**RNF-009.3** — Los eventos de seguridad (login fallido, cambio de contraseña, rate limit alcanzado) deben registrarse en un log estructurado.

---

# RNF-010 — Respaldo y Recuperación ante Desastres

**Tipo**: Requisito No Funcional de Respaldo y Recuperación

## Requisitos Específicos

**RNF-010.1** — La base de datos debe contar con copias de seguridad automáticas diarias.

**RNF-010.2** — Las copias de seguridad deben conservarse por un mínimo de 30 días.

**RNF-010.3** — Debe existir un procedimiento documentado de restauración ante pérdida de datos.

---

# RNF-011 — Gestión de Errores y Resiliencia

**Tipo**: Requisito No Funcional de Resiliencia

## Requisitos Específicos

**RNF-011.1** — Todo error no controlado debe responder con un mensaje genérico al cliente, sin exponer detalles internos (stack trace).

**RNF-011.2** — Los errores de integración con la pasarela de pagos no deben dejar pedidos en estado inconsistente.

**RNF-011.3** — El sistema debe reintentar automáticamente operaciones idempotentes ante fallos transitorios de red.

---

# RNF-012 — Monitoreo y Observabilidad

**Tipo**: Requisito No Funcional de Monitoreo y Observabilidad

## Requisitos Específicos

**RNF-012.1** — El backend debe exponer un endpoint de `healthcheck` para verificar su disponibilidad.

**RNF-012.2** — Los tiempos de respuesta de los endpoints críticos deben poder monitorearse.

**RNF-012.3** — Los errores 5xx deben generar una alerta para el equipo de desarrollo.

---

# RNF-013 — Confidencialidad de Datos

**Tipo**: Requisito No Funcional de Confidencialidad

## Requisitos Específicos

**RNF-013.1** — Los datos personales de los usuarios (dirección, teléfono) solo deben ser visibles para su propietario y para administradores autorizados.

**RNF-013.2** — Las variables sensibles (credenciales de base de datos, secretos JWT, llaves de pasarela) deben gestionarse mediante variables de entorno, nunca en el código fuente.

**RNF-013.3** — El acceso a Supabase/PostgreSQL en producción debe restringirse por IP o mediante conexión cifrada.

---

# RNF-014 — Integridad de Datos

**Tipo**: Requisito No Funcional de Integridad de Datos

## Requisitos Específicos

**RNF-014.1** — Cada tabla debe tener una clave primaria definida.

**RNF-014.2** — No se permiten valores nulos en campos críticos (precio, stock, email).

**RNF-014.3** — Las relaciones entre tablas deben protegerse con llaves foráneas correctamente definidas en el esquema de Prisma.

---

# RNF-015 — Capacidad y Concurrencia

**Tipo**: Requisito No Funcional de Capacidad y Concurrencia

## Requisitos Específicos

**RNF-015.1** — El sistema debe procesar hasta 50 transacciones de checkout por minuto sin errores ni pérdida de información.

**RNF-015.2** — Las actualizaciones de stock deben protegerse contra condiciones de carrera mediante transacciones o bloqueo optimista.

**RNF-015.3** — El carrito de compras debe soportar múltiples sesiones concurrentes del mismo usuario sin duplicar ítems.

---

# RNF-016 — Consistencia Visual y de Diseño

**Tipo**: Requisito No Funcional de Diseño

## Requisitos Específicos

**RNF-016.1** — La interfaz debe mantener un mismo estilo visual (colores sólidos, tipografía sans-serif) en todas las vistas.

**RNF-016.2** — Los espaciados y tamaños de componentes deben ser uniformes en todo el sistema.

**RNF-016.3** — Los botones principales deben alinearse consistentemente a la derecha según lo definido en Restricciones.md.

---

# RNF-017 — Documentación Técnica

**Tipo**: Requisito No Funcional de Documentación

## Requisitos Específicos

**RNF-017.1** — Cada módulo del backend debe documentar sus endpoints, entradas y salidas.

**RNF-017.2** — El repositorio debe mantener actualizada la carpeta `docs/` con HU, RF y RNF vigentes.

**RNF-017.3** — Los cambios de esquema en la base de datos deben reflejarse en `schema.prisma` y documentarse en `database-schema`.

---

# RNF-018 — Control de Versiones

**Tipo**: Requisito No Funcional de Control de Versiones

## Requisitos Específicos

**RNF-018.1** — Las ramas permitidas son `main` (estable) y `dev` (desarrollo).

**RNF-018.2** — No se permite hacer commits directamente en `main`.

**RNF-018.3** — No se permite el uso de `git push --force` sobre ramas compartidas.

---

# RNF-019 — Pruebas y Calidad de Código

**Tipo**: Requisito No Funcional de Calidad

## Requisitos Específicos

**RNF-019.1** — Los módulos críticos (autenticación, pagos, inventario) deben contar con pruebas unitarias.

**RNF-019.2** — El proyecto debe pasar `pnpm lint` sin errores antes de cada despliegue.

**RNF-019.3** — No se permite desactivar reglas estrictas de TypeScript sin justificación documentada.

---

# RNF-020 — Gestión de Sesiones

**Tipo**: Requisito No Funcional de Gestión de Sesiones

## Requisitos Específicos

**RNF-020.1** — La sesión del usuario debe cerrarse automáticamente después de 15 minutos de inactividad.

**RNF-020.2** — El token de sesión (JWT) debe invalidarse al cerrar sesión explícitamente.

**RNF-020.3** — Un usuario no puede acceder a rutas protegidas de otro rol distinto al suyo.

---

# RNF-021 — Protección contra Ataques (OWASP)

**Tipo**: Requisito No Funcional de Seguridad Aplicada

## Requisitos Específicos

**RNF-021.1** — El sistema debe sanear toda entrada de usuario para prevenir inyección SQL y XSS.

**RNF-021.2** — Las cabeceras HTTP de seguridad deben configurarse con `helmet` (CSP, HSTS, X-Frame-Options).

**RNF-021.3** — Los formularios sensibles deben protegerse contra CSRF mediante tokens o cabeceras `SameSite`.

---

# RNF-022 — Cifrado de Datos en Tránsito y en Reposo

**Tipo**: Requisito No Funcional de Cifrado

## Requisitos Específicos

**RNF-022.1** — Toda comunicación entre cliente y servidor debe realizarse mediante HTTPS (TLS 1.2 o superior) en producción.

**RNF-022.2** — Las contraseñas y tokens sensibles deben almacenarse cifrados o hasheados, nunca en texto plano.

**RNF-022.3** — Las copias de seguridad de la base de datos deben almacenarse cifradas en reposo.

---

# RNF-023 — Cumplimiento Normativo y Legal

**Tipo**: Requisito No Funcional de Cumplimiento

## Requisitos Específicos

**RNF-023.1** — El tratamiento de datos personales debe informarse al usuario mediante una política de privacidad accesible.

**RNF-023.2** — El usuario debe poder solicitar la eliminación de su cuenta y datos personales.

**RNF-023.3** — Las facturas generadas deben incluir la información mínima requerida por la normativa comercial vigente en Colombia.

---

# RNF-024 — Compatibilidad con Navegadores

**Tipo**: Requisito No Funcional de Compatibilidad

## Requisitos Específicos

**RNF-024.1** — El frontend debe funcionar correctamente en las últimas dos versiones estables de Chrome, Firefox, Edge y Safari.

**RNF-024.2** — Las funcionalidades críticas (carrito, checkout) no deben depender de APIs experimentales del navegador.

---

# RNF-025 — Responsividad (Diseño Adaptable)

**Tipo**: Requisito No Funcional de Usabilidad Móvil

## Requisitos Específicos

**RNF-025.1** — El catálogo y el checkout deben ser completamente funcionales en dispositivos móviles (viewport desde 320px).

**RNF-025.2** — Los elementos táctiles (botones, enlaces) deben tener un área mínima de 44x44px en vistas móviles.

---

# RNF-026 — Moneda y Formato Regional

**Tipo**: Requisito No Funcional de Localización

## Requisitos Específicos

**RNF-026.1** — Todos los montos monetarios deben mostrarse en pesos colombianos (COP) con el formato regional correspondiente.

**RNF-026.2** — Las fechas deben mostrarse en formato `dd/mm/aaaa` en toda la interfaz.

**RNF-026.3** — El idioma único soportado por el sistema es español, según lo definido en Restricciones.md.

---

# RNF-027 — Rendimiento de Base de Datos

**Tipo**: Requisito No Funcional de Rendimiento de Datos

## Requisitos Específicos

**RNF-027.1** — Las consultas frecuentes (catálogo, pedidos por cliente, movimientos por producto) deben contar con índices apropiados.

**RNF-027.2** — Las consultas de reportes no deben bloquear las operaciones transaccionales del checkout.

**RNF-027.3** — El tamaño de las respuestas paginadas no debe exceder los 50 registros por página por defecto.

---

# RNF-028 — Gestión de Logs

**Tipo**: Requisito No Funcional de Logging

## Requisitos Específicos

**RNF-028.1** — Los logs de aplicación deben registrarse en formato estructurado (JSON) para facilitar su análisis.

**RNF-028.2** — Los logs no deben contener contraseñas, tokens ni datos de tarjetas de pago.

**RNF-028.3** — Los logs de error deben incluir un identificador de solicitud para facilitar la trazabilidad.

---

# RNF-029 — Despliegue y CI/CD

**Tipo**: Requisito No Funcional de Despliegue

## Requisitos Específicos

**RNF-029.1** — El proceso de build (`pnpm build`) debe ejecutarse sin errores antes de cualquier despliegue a producción.

**RNF-029.2** — Las migraciones de base de datos (Prisma) deben aplicarse de forma controlada antes de desplegar nueva funcionalidad.

**RNF-029.3** — Debe existir un entorno de pruebas (staging) separado del entorno de producción.

---

# RNF-030 — Costos y Eficiencia de Infraestructura

**Tipo**: Requisito No Funcional de Eficiencia

## Requisitos Específicos

**RNF-030.1** — El uso del procesador del servidor debe mantenerse por debajo del 80% durante picos de carga.

**RNF-030.2** — Las imágenes de producto deben optimizarse (compresión y formato WEBP) para reducir el consumo de ancho de banda.

**RNF-030.3** — El almacenamiento de archivos (imágenes) debe delegarse a un servicio externo (ej. Supabase Storage) en lugar del servidor de aplicación.

---
